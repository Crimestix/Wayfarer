## 0. Das Wichtigste in zehn Sätzen

1. Die Rust-Seite ist heute ein **dünner, misstrauischer Bote**: fest eingebaute Adresse, Schlüssel
   aus dem Schlüsselbund, Eingaben geprüft, Antwort als `{ status, body }` unverändert zurück. Die
   Auswertung (Fehlerarten, Sätze, Wiederholen) liegt in TypeScript und ist dort getestet.
2. HTTP: `reqwest 0.13` ohne Vorgaben, TLS über `rustls` + `ring`. **Kein `json`-Feature, kein
   `stream`, kein `gzip`, kein direktes `tokio`.** Antworten werden stückweise mit Obergrenze gelesen.
3. Schlüsselbund: Crate `keyring 4` (v1-Modus), Dienst `app.wayfarer.desktop`, Konten `Claude-Key`
   und `LegendKeeper-Key`. Der Code dafür steht **zweimal fast wortgleich** (`ai.rs`, `legendkeeper.rs`).
4. Ein neuer Befehl braucht **fünf Stellen**: `build.rs` (COMMANDS), `lib.rs` (Funktion +
   `generate_handler!`), `capabilities/main.json` (`allow-…`), `platform.ts` (Vertrag + Hülle),
   `tests.rs` (Vertragstest). Die Datei unter `permissions/autogenerated/` entsteht beim Bau von selbst
   und wird eingecheckt.
5. CSP: Das Fenster darf nur `'self'` und `ipc:` ansprechen – **GitHub ist von der Oberfläche aus
   nicht erreichbar**, alles muss über Rust. An der CSP muss nichts geändert werden.
6. Fortschritt läuft heute **ohne Ereignisse**: Die Oberfläche ruft viele kleine Befehle
   (`media_fetch` je Bild, vier zugleich) und zählt selbst; Abbruch = keine weiteren mehr starten.
   Ereignisse Rust → Oberfläche gibt es aber schon (`store-changed`, `close-requested`) und sind erlaubt.
7. Netz-Tests: kein Mock-Crate. Jede Netz-Funktion nimmt **Client und Basisadresse als Parameter**;
   Tests starten einen winzigen `TcpListener` auf `127.0.0.1:0` und übergeben dessen Adresse.
8. Der Kampagnenordner wird überwacht; was Rust dort hineinschreibt, kommt über `store-changed` von
   selbst im Spielstand an – **außer** für Dateien, für die noch Ungespeichertes wartet (siehe Fallstricke).
9. Startbildschirm (`shell/Welcome.tsx`): Ordner wählen → öffnen oder „Dieser Ordner ist noch leer“
   mit zwei Wahlkarten. Dort gehört die dritte Karte „Kampagne von GitHub holen“ hin.
10. Für GitHub fehlen: SHA-1 (Git-Blob-Kennung) und base64 als **direkte** Abhängigkeit. Beides liegt
    schon in `Cargo.lock` (`ring 0.17.14` kann SHA-1, `base64 0.23.1` kommt über reqwest) – es muss
    nichts Neues heruntergeladen werden.

### 1.3 Fehlerbehandlung

- **Jeder Befehl gibt `Result<T, String>` zurück; der Fehler ist ein fertiger deutscher Satz.**
- Ein HTTP-Status ist **kein** Fehler: 401, 404, 429 kommen als `{ status, body }` zurück
  (`legendkeeper.rs` 260–261: „ein Fehler bedeutet, dass gar keine Antwort der API zustande kam“).
  Ausnahme `media.rs` 178–187: dort wird der Status auf der Rust-Seite in einen Satz übersetzt.
- Netzfehler werden in drei Sätze sortiert (`legendkeeper.rs` 246–258):
  `is_redirect()` → „… leitet auf eine Adresse außerhalb seiner API weiter. Der Key wurde nicht
  weitergegeben.“, `is_timeout()` → „… hat nicht rechtzeitig geantwortet …“, `is_connect()` →
  „… ist nicht erreichbar. Besteht eine Internetverbindung?“, sonst „Die Verbindung … ist
  fehlgeschlagen. Der Key bleibt gespeichert; bitte erneut versuchen.“
- Der Schlüssel erscheint nie in einer Fehlermeldung (Test `legendkeeper.rs` 552: `!err.contains("geheim")`).
- **Die Oberfläche erkennt „kein Netz“ am Wortlaut** (`features/legendkeeper/errors.ts` 134–145):
  `/nicht rechtzeitig|Zeitüberschreitung|timed? ?out/` → `timeout`,
  `/nicht erreichbar|Internetverbindung|…/` → `offline`. Wer für GitHub dieselbe Unterscheidung will
  („ohne Netz am Tisch läuft alles weiter“), sollte **nicht** wieder Sätze auslesen, sondern eine Art
  mitgeben, z. B. `Result<SyncReply, SyncError>` mit `#[derive(Serialize)] struct SyncError { kind, message }`
  – Tauri reicht jeden serialisierbaren Fehler durch. Achtung: `platform.ts` 35–42 macht aus allem,
  was kein `Error` und kein Text ist, „Unerwarteter Fehler in der App.“ – die Hülle `invoke` müsste
  für solche Fehler erweitert werden.
- Retry-After: Die Rust-Seite reicht **keine Kopfzeilen** durch (`LkResponse` hat nur `status`, `body`).
  Für GitHub (Bremse, `x-ratelimit-remaining`, `retry-after`) müsste die Antwort um die paar nötigen
  Kopfzeilen wachsen.

### 1.4 Weg zur Oberfläche

`lib.rs` 129–140 (LegendKeeper) ist das Muster für „Schlüssel holen, dann ins Netz“:

```rust
#[tauri::command]
async fn lk_get<R: Runtime>(app: AppHandle<R>, path: String, query: Option<Value>) -> Result<LkResponse, String> {
    let reader = app.clone();
    let key = blocking(move || reader.state::<LegendKeeper>().keys.get())
        .await?
        .ok_or_else(|| "Es ist noch kein LegendKeeper-Key hinterlegt.".to_string())?;
    app.state::<LegendKeeper>().get(&key, &path, query.as_ref()).await
}
```

- `blocking(...)` (`lib.rs` 30–36) = `tauri::async_runtime::spawn_blocking` – für **alles**, was Dateien
  oder den Schlüsselbund anfasst („damit ein träges Cloud-Laufwerk nichts blockiert“).
- Zustand über `.manage(X::default())` (`lib.rs` 309–313) und `app.state::<X>()`.
- In TS: `platform.ts` 35–42 `invoke<T>()` wandelt den Satz in `new Error(satz)`; die Oberfläche zeigt
  `error.message`. Ereignisse: `listen` aus `@tauri-apps/api/event` (`platform.ts` 79, 198).
- Der Kommentar in `features/legendkeeper/client.ts` 288 ist wichtig: „Ein laufender Abruf der
  App-Seite lässt sich nicht stoppen; sein Ergebnis wird dann verworfen.“ – ein `invoke` hat kein
  Abbrechen. TS setzt selbst eine Zeitgrenze darum (`guarded`, `DESKTOP_TIMEOUT_MS = 40_000`, Z. 82, 266–281).

### 2.4 Verhalten je System (aus dem Crate gelesen, lokale Quelle `keyring-4.2.0/src/v1.rs` 110–121)


- **Windows:** Anmeldeinformationsverwaltung („Windows-Anmeldeinformationen“), je Benutzer. Kein Dialog.

- **Linux (nur CI):** Secret Service; in der Prüfung bei GitHub gibt es keinen – deshalb testet
  nichts den echten Schlüsselbund.
- Der Schlüssel wird nur einmal je Programmlauf gelesen (Zwischenspeicher im `Mutex`).

## 6. Lange Arbeiten mit Fortschritt und Abbruch

### 6.1 Wie es die Bilder machen (das einzige Vorbild)

`media_fetch` ist **ein Bild je Aufruf**, ohne Ereignisse (`lib.rs` 183–192, `media.rs` 61–76):
prüft Namen und Adresse, überspringt Vorhandenes (`meta.len() > 0` → gibt die Größe zurück), lädt,
prüft „ist ein Bild“ (`mime_of`), schreibt atomar, gibt die Größe zurück.

Schleife, Zählen und Abbruch liegen in TS (`features/wiki/media.ts` 58–95):

```ts
const PARALLEL = 4;
export async function fetchImages(root, items, onProgress, signal?, fetchOne = mediaFetch): Promise<FetchProgress> {
  const queue = items.filter((item) => !hasLocalMedia(item.name));
  const progress: FetchProgress = { done: 0, total: queue.length, bytes: 0, failed: [] };
  …
  const work = async () => {
    while (next < queue.length && !signal?.aborted) {      // Abbruch: nichts Neues beginnen
      const item = queue[next++]!;
      try { const size = await fetchOne(root, item.url, item.name); progress.bytes += size; addLocalMedia(item.name); }
      catch (error) { progress.failed.push({ item, reason: … }); }   // ein Fehlschlag hält die übrigen nicht auf
      progress.done++; onProgress({ ...progress, failed: [...progress.failed] });
    }
  };
  await Promise.all(Array.from({ length: Math.min(PARALLEL, queue.length) }, work));
```

Anzeige `MediaSection.tsx`: `AbortController` in einem `useRef` (26, 38–48), Knopf „Anhalten“ (65),
Balken (89–100: „Hole Bilder … 12 von 481 · 310 MB“ / „Angehalten:“ / „Fertig:“), danach `Notice`
mit „Noch einmal versuchen“ (108–123: „ein zweiter Versuch holt nur, was fehlt“).
Gleiches Muster beim KI-Leser: `stop = useRef(false)`, Schleife in der Komponente
(`AiSection.tsx` 30, 82–118). **Eigenschaften:** wiederholbar ohne Schaden, Abbruch nur zwischen

### 6.3 Zwei gangbare Muster für den Abgleich

**Muster A – „viele kleine Befehle, TS führt“ (wie die Bilder; passt am besten zum Bestand).**
Rust bietet wenige, einzeln wiederholbare Schritte, z. B.:
`sync_local({ root })` (Liste aller Dateien mit Git-Blob-Kennung – auf der Rust-Seite gerechnet,
damit nicht jeder Inhalt durchs Fenster muss), `sync_remote({ repo })` (Stand des Zweigs + Baum),
`sync_pull_file({ root, repo, path, sha, expectLocal })`, `sync_push({ root, repo, base, changes })`.
Die Entscheidung je Datei (gemeinsamer Stand / hier / dort → nichts, holen, hochladen, löschen,
Konflikt) ist dann eine **reine TS-Funktion mit Vitest** – so verlangt es CLAUDE.md („Fachlogik als
reine Funktion … mit Test. Komponenten rechnen nicht selbst.“). Fortschritt und Abbruch wie in 6.1.
Nachteil: Beim Schließen muss die Oberfläche noch leben; der Schlüssel bleibt trotzdem in Rust.

**Muster B – „ein langer Befehl in Rust mit Ereignissen“.**
`sync_run` startet eine Aufgabe (`tauri::async_runtime::spawn`), meldet `app.emit("sync-progress",
{ phase, done, total })`, Abbruch über `sync_cancel` und ein `AtomicBool` im verwalteten Zustand
(wie `WatchState`/`Closing`: `Mutex` in `.manage(…)`). Das gibt es im Projekt noch nicht; die
Entscheidungslogik läge dann in Rust (`cargo test`). Vorteil: ein Abgleich läuft auch zu Ende, wenn
das Fenster schon weg will. Ein `invoke` selbst ist nicht abbrechbar (6.1/1.4).

Beides verträgt sich: Entscheidung in TS (A), Hoch-/Herunterladen als wenige größere Rust-Befehle
mit Ereignis für den Balken.

### 6.4 Was die Auslöser im Bestand vorfinden

- **Beim Öffnen:** nach `CampaignDb.open` in `App.tsx` 67–88 (dort hängt schon `loadLocalMedia`).
  Besser **vor** dem Öffnen holen (dann liest `readAll` gleich den neuen Stand) – aber ohne Netz
  darf das den Start nicht aufhalten: kurze Zeitgrenze, sonst öffnen und nachholen.
- **Nach Änderungen (gebündelt):** `db.ts` schreibt 250 ms nach der letzten Änderung (`enqueue`
  266–272, `flush` 293–323). Einen Haken „nach dem Schreiben“ gibt es nicht; `db.subscribeStatus`
  (152–157) meldet den Wechsel auf `'saved'` – daran lässt sich ein eigener, viel längerer
  Zeitgeber (etwa eine halbe Minute Ruhe) hängen. Oder Rust lauscht selbst auf den Wächter.
- **Beim Schließen:** `onAppClosing(handler)` (`platform.ts` 184–189). Ablauf `window.rs` 5–12:
  Fenster will zu → Ereignis → Oberfläche antwortet binnen **1,5 s** (`ANSWER_GRACE`, Z. 29) mit
  `saving` → danach **keine Frist mehr**, bis `saved`/`unsaved` kommt (`tests.rs` 297–302).
  Zweiter Schließversuch währenddessen → Rückfrage „Wayfarer speichert noch. Wenn du jetzt schließt,
  gehen die letzten Änderungen womöglich verloren.“ (`window.rs` 183–186). Antwortet ein Handler
  `false` → „Die letzten Änderungen ließen sich nicht speichern – vermutlich ist der Kampagnenordner
  gerade nicht erreichbar. Wenn du Wayfarer jetzt schließt, gehen sie verloren.“ (179–182).
  **Beide Sätze sind für einen Abgleich falsch** – siehe Fallstricke.
- **Per Knopf:** `ActionRow` „Jetzt abgleichen“ in den Einstellungen und das Zeichen in der Leiste.

- Vertragstests in `src/tests.rs` (`lib.rs` 350–351: `#[cfg(test)] mod tests;`): bauen die **echte
  App ohne Fenster** – `crate::wayfarer(mock_builder()).build(crate::context())` (Z. 22–26) – also mit

  Deshalb ist in `Cargo.toml` 43 `tauri = { features = ["test"] }` als Entwicklungsabhängigkeit da

- Dateien: `tempfile::TempDir` als Kampagnenordner.
- Asynchrones in Tests: `tauri::async_runtime::block_on(future)` (`ai.rs` 372–374, `legendkeeper.rs` 472–474).

### 7.2 Falscher Server: kein Crate, kein Trait – die Adresse ist ein Parameter

Die „Abstraktion“ ist schlicht: **freie Funktionen nehmen Client und Basisadresse**; nur die
Zustands-Struktur kennt die echte Adresse fest und hat keinen Setzer.

```rust
// legendkeeper.rs
pub fn build_client(base: &Url) -> Result<Client, String>                                   // 217
pub async fn fetch(client: &Client, base: &Url, key: &str, path: &str, query: Option<&Value>) -> Result<LkResponse, String>   // 262
pub struct LegendKeeper { pub keys: KeyCache, base: Url, client: Mutex<Option<Client>> }     // 292–296, base privat
impl Default for LegendKeeper { … base: Url::parse(API_BASE).expect("feste Adresse") … }     // 298–306
```

Tests bauen einen winzigen Gegenpart mit `std::net::TcpListener::bind("127.0.0.1:0")` in einem Thread:

- `legendkeeper.rs` 434–463 `serve(respond: impl Fn(&str) -> String)`: **Schleife über alle
  Verbindungen**, antwortet je nach erster Zeile der Anfrage, reicht die Kopfzeilen über einen
  `mpsc`-Kanal zurück. Liest **keinen** Anfragekörper (nur GET).
- `ai.rs` 336–363 `serve(reply: String)`: **eine** Verbindung, liest den Körper nach
  `Content-Length`, gibt `(Kopfzeilen, Körper)` zurück.
- Antworten von Hand: `"HTTP/1.1 200 OK\r\nContent-Length: …\r\nConnection: close\r\n\r\n…"`
  (`ai.rs` 365–370, `legendkeeper.rs` 465–470). `Connection: close` → jede Anfrage eine neue Verbindung.
- Was damit schon geprüft wird (als Liste für GitHub übernehmen): Schlüssel und Kopfzeilen kommen an
  (`ai.rs` 376–397, `legendkeeper.rs` 476–509), Fehlerstatus werden durchgereicht (399–407 / 511–518),
  Weiterleitungen nach draußen werden verweigert und die fremde Adresse sieht nie eine Anfrage
  (`legendkeeper.rs` 536–558), „nicht erreichbar“ in einfachen Worten (560–569: Port öffnen, schließen, ansprechen).
- Möglich ist das nur, weil `https_only(base.scheme() == "https")` und `.no_proxy()` für http gelten
  (1.2). `media.rs` hat das **nicht** (`build_client()` ohne Parameter, `https_only(true)`) – dort ist
  das Herunterladen selbst ungetestet, nur Namen, Adressen, Erkennen und Ablegen.

**Für GitHub** braucht der Gegenpart beides zusammen: Schleife (viele Anfragen hintereinander) **und**
Körper lesen (POST/PATCH), dazu ein kleines Repository im Speicher (`Mutex<HashMap<…>>`: Blobs, Bäume,
Stand des Zweigs), damit sich ganze Abläufe prüfen lassen: holen, hochladen, „der andere war
schneller“ (PATCH des Zweigs antwortet 422), 401, 404, Bremse, abgebrochene Verbindung mitten im
Ablauf. Das sind rund 80 Zeilen Testhilfe nach den beiden Vorbildern; ein Mock-Crate wäre eine neue
Abhängigkeit „ohne guten Grund“. Die GitHub-Funktionen also so schneiden:
`pub async fn get_tree(client: &Client, api: &Url, key: &str, repo: &Repo, sha: &str) -> …` und
`struct GitHub { keys, api: Url /* privat, Default = https://api.github.com */, client }`.

## 8. Was für GitHub darüber hinaus zu beachten ist

(8.1–8.3 folgen aus dem gelesenen Code. 8.4 stammt aus Kenntnis der GitHub-Schnittstelle, **nicht**
aus dem Projekt und nicht im Netz nachgeschlagen – vor dem Bau gegen die Dokumentation prüfen.)

### 8.1 Was die Ablage vorgibt

- Erlaubte Pfade: `store::check_rel_path` (`store.rs` 80–112): „/“-getrennt, höchstens 4 Teile,
  ≤ 240 Zeichen, nichts Verstecktes, keine Windows-Sondernamen, **nur `.json`**. Alles, was aus dem
  Repository kommt, muss **vor dem Schreiben** hier durch (`store::resolve`, 116–131, lehnt auch
  Verknüpfungen ab). Ein fremder Pfad im Repository (`README.md`, `.gitattributes`, `../x`) wird
  übergangen, nie geschrieben, nie gelöscht.
- Bilder: `media/<name>` mit `media::check_name` (`media.rs` 83–104; nur png, jpg, jpeg, webp, gif,
  avif) und `media::path_of` (107–115). `media::save` (219–225) legt nur ab, was wirklich ein Bild ist.
  Die Ablage sieht `media/` nicht (`store.rs` nimmt nur JSON), der Wächter meldet es nicht.
- Wiederverwendbar und `pub`: `store::check_root`, `resolve`, `to_rel_path`, `list`, `read_all`,
  `write_atomic` (323–345: temporäre Datei `.wayfarer-<name>.<pid>-<n>.tmp` im selben Ordner, dann
  umbenennen; unter Windows bis zu 8 Versuche bei gesperrter Datei, `patiently` 162–173), `remove`.
- Grenzen: Datei > 16 MB wird beim Einlesen **übergangen** (Z. 21, 284), > 100 000 Dateien oder
  > 512 MB → Fehler „zu viele Dateien“ (23–24, 288–290).
- Kennung rechnen über die **rohen Bytes auf der Platte**, nicht über den gelesenen Text:
  `decode` (189–199) entfernt ein BOM und ersetzt kaputte Zeichen.
- Geschrieben wird von TS immer `JSON.stringify(doc, null, 1) + '\n'` (`db.ts` 45) – gleiche Bytes
  auf Mac und Windows, keine Zeilenenden-Frage, solange niemand das Repository mit dem
  Git-Programm unter Windows auscheckt (`autocrlf`).
- Liegengebliebene `.wayfarer-*.tmp`, älter als 10 Minuten, räumt `walk` weg (26–29, 201–211, 235–239)
  – eine Datei für den gemeinsamen Stand darf **nicht** so heißen.

### 8.2 Wie Geholtes im laufenden Spielstand ankommt

Schreibt Rust in den Ordner, meldet der Wächter `store-changed` (entprellt: 300 ms Ruhe, höchstens
2 s, `watch.rs` 18–21), und `CampaignDb.reload` (`db.ts` 331–342) übernimmt:

```ts
for (const path of paths) {
  if (this.pending.has(path)) continue;                               // ← Ungespeichertes hat Vorrang
  const content = await this.store.read(path);
  if (content === (this.lastWritten.get(path) ?? null)) continue;     // eigener Schreibvorgang: nichts tun
  …
  changed = this.applyExternal(path, content) || changed;
}
```

Das ist der fertige Weg „Änderung von außen“ – ein eigener Befehl „Spielstand neu laden“ ist nicht
nötig. Gelöschte Dokumente werden entfernt (362–366); ein gelöschtes `campaign.json`/`state.json`
wird ignoriert (344–356). Ungültiges landet in `db.problems` und wird nie überschrieben.

### 8.3 Einstellungen je Rechner

`config_set` schreibt die **ganze** Datei neu aus einem einzigen Feld (`lib.rs` 52–57):
```rust
blocking(move || config::save(&dir, &AppConfig { campaign_dir })).await
```
und TS ruft `invoke('config_set', { ...config })` (`platform.ts` 52). Kämen Repository/Zweig als
Felder in `AppConfig` dazu, würde **jeder Ordnerwechsel sie löschen**. Also: eigene Datei
(`sync.json`) mit eigenen Befehlen – oder `config_set` zu „lesen, ändern, schreiben“ umbauen.
Für den gemeinsamen Stand (Pfad → Blob-Kennung, dazu die Kennung des letzten gemeinsamen Commits)
gibt es zwei Orte:
- im Einstellungsordner der App, je Kampagnenordner eine Datei (gehört klar zu „diesem Rechner“;
  geht verloren, wenn der Ordner umzieht → dann sieht alles wie „beide geändert“ aus, was aber über
  gleiche Kennungen wieder zusammenfällt), oder
- versteckt im Kampagnenordner (`.wayfarer-sync/…`: Ablage und Wächter übergehen alles mit Punkt;
  zieht mit dem Ordner um; darf nie hochgeladen werden und nicht auf `.tmp` enden).

### 8.4 GitHub-Schnittstelle (aus Kenntnis, zu prüfen)

- Basis `https://api.github.com`; Kopfzeilen `Authorization: Bearer <Schlüssel>`,
  `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: <Datum>` (aktuellen Wert nachsehen),
  `User-Agent` (Pflicht – vorhanden).
- Ablauf über „Git-Daten“ (so steht es im alten Plan, `docs/WEITERARBEIT.md` 168: „Bäume/Blobs, kein
  libgit2“): Zweig lesen `GET /repos/{b}/{n}/git/ref/heads/{zweig}` → Commit → Baum
  `GET …/git/trees/{sha}?recursive=1` (liefert Pfad + Blob-Kennung aller Dateien; bei sehr großen
  Bäumen `truncated: true`) → fehlende Blobs `GET …/git/blobs/{sha}` (Inhalt base64) → hochladen:
  `POST …/git/trees` mit `base_tree` und Einträgen (`path`, `mode: "100644"`, `type: "blob"`,
  entweder `sha` oder bei Text direkt `content`; Löschen mit `sha: null`) → `POST …/git/commits` →
  `PATCH …/git/refs/heads/{zweig}` **ohne** `force`. Lehnt GitHub das ab (422), war der andere
  Rechner schneller: neu holen, neu vergleichen – das ist die Sperre gegen stilles Überschreiben.
- Git-Blob-Kennung = SHA-1 über `"blob " + Länge in Bytes + "\0" + Inhalt`. Damit lässt sich der
  Ordner mit dem Baum vergleichen, ohne etwas herunterzuladen. JSON-Dateien können als `content`
  im Baum mitgehen (kein base64, keine Einzelanfrage je Datei); base64 braucht es für das Lesen von
  Blobs und für Bilder.
- **Leeres Repository:** Die Git-Daten-Befehle antworten dort mit 409. Der allererste Commit muss
  über „Inhalte“ (`PUT …/contents/{pfad}`) entstehen – oder die Anleitung lässt das Repository mit
  einer README anlegen (die Wayfarer dann als fremde Datei in Ruhe lässt).
- **Zahl der Anfragen:** 5000 je Stunde mit Schlüssel, dazu eine Bremse für schreibende Anfragen in
  kurzer Folge. Hochladen bleibt klein (ein Baum trägt viele Dateien; bei Tausenden in Portionen mit
  `base_tree` verketten). **Der Erstabruf am zweiten Rechner ist der kritische Fall:** je Datei ein
  Blob-Abruf – bei mehreren Tausend Dateien (Artikel, frühere Fassungen, Chronik) kommt man der
  Grenze nahe und es dauert. Auswege: das Archiv des Zweigs in einem Abruf
  (`GET …/zipball/{zweig}`; leitet auf einen anderen Rechnernamen weiter → eigene Regel für
  Weiterleitungen nötig, der Schlüssel darf nicht mitwandern; braucht ein `zip`-Crate) oder
  gebündelte Abfragen. Die Zahl der Dateien im echten Kampagnenordner kenne ich nicht (Ordner tabu) –
  **vor der Entscheidung zählen lassen.**
- **Bilder:** laut `docs/WEITERARBEIT.md` 326–333 gemessen 481 Bilder, 1,35 GB – „für den Abgleich
  über GitHub … zu groß“. GitHub lehnt Dateien über 100 MB ab und mahnt bei Repositories über etwa
  1 GB. `media.rs` erlaubt bis 96 MB je Bild. Der Auftrag nennt `media/` als Teil des Spielstands –
  das ist ein offener Widerspruch zum alten Plan und braucht eine Entscheidung (nur JSON abgleichen
  und Bilder wie bisher je Rechner holen; oder Bilder mit eigener Obergrenze, einzeln und zuletzt).
- **Schlüssel:** fein eingestellt (`github_pat_…`), nur dieses eine Repository, Berechtigung
  „Contents: Read and write“. Solche Schlüssel **laufen ab** – die Oberfläche braucht dafür einen
  klaren Satz bei 401 („Der Zugangsschlüssel ist abgelaufen oder wurde widerrufen. Erzeuge bei GitHub
  einen neuen und trage ihn hier ein.“) und der Abgleich muss dann ruhen, nicht stören.

## 9. Fallstricke (Reihenfolge nach Gewicht)

1. **Ungespeichertes überschreibt Geholtes.** `db.reload` überspringt Pfade, für die noch etwas
   wartet (`db.ts` 334) – der nächste `flush` schreibt dann die alte eigene Fassung über die geholte.
   Vor jedem Abgleich `await db.flush()` und `db.hasUnsavedChanges()` prüfen; und auf der Rust-Seite
   jede Datei nur ersetzen, wenn ihre Kennung **unmittelbar vorher** noch die erwartete ist
   (vergleichen-dann-schreiben), sonst → Konflikt. Zwischen Vergleich und Schreiben kann der
   Spielleiter weitertippen (250 ms bis zum Schreiben).
2. **`state.json` ändert sich bei fast jedem Handgriff** (Zeit, Ort, Brett-Lagen …), `campaign.json`
   bei jeder Einstellung. Haben beide Rechner ohne Netz gearbeitet, ist ein Konflikt in `state.json`
   praktisch sicher. Die Regel „je Datei entscheidet der Spielleiter“ braucht für diese beiden
   Dateien eine besonders gute Darstellung (was unterscheidet sich: Weltzeit, Ort …), sonst wird
   der Dialog zur Dauerplage. Jedes Dokument trägt `rev` und `updated` (`db.ts` 163, 190–195) – gut
   zum Zeigen, **nicht** zum stillen Entscheiden.
3. **Schließen:** Meldet der Abgleich über `onAppClosing` `false`, erscheint „Die letzten Änderungen
   ließen sich nicht speichern … gehen sie verloren“ – falsch und beunruhigend, denn alles liegt
   sicher im Ordner. Ein Abgleich beim Schließen muss also **immer `true` melden** (mit eigener,
   kurzer Zeitgrenze; ohne Netz sofort aufgeben und beim nächsten Öffnen nachholen) oder `window.rs`
   bekommt eine eigene Antwort/Frage. Und: Während des Abgleichs gilt die Phase „Saving“ – ein
   zweiter Klick aufs Schließen zeigt „Wayfarer speichert noch“. Der erste `app_close('saving')`
   muss binnen 1,5 s kommen, sonst schließt das Fenster von selbst (`window.rs` 29, 102–107).
4. **`config_set` löscht fremde Felder** (8.3). Repository-Angaben nicht in `AppConfig` legen, ohne
   den Befehl umzubauen.
5. **Reihenfolge beim neuen Befehl:** erst `build.rs`, dann `capabilities/main.json`. Vergessenes
   `allow-…` → Befehl antwortet zur Laufzeit „not allowed“ (fällt erst in der echten App oder im
   Vertragstest auf); `allow-…` ohne Eintrag in `build.rs` → Bau bricht ab.
6. **Die erzeugten Berechtigungsdateien stehen dauernd als „geändert“ im Arbeitsbaum** (alle 18, auch
   jetzt): Der Bau schreibt sie mit LF, Git erwartet hier CRLF; `git diff` zeigt keinen inhaltlichen
   Unterschied, nur die Warnung „LF will be replaced by CRLF“. Nicht irritieren lassen, nicht
   „reparieren“; nach dem ersten Bau mit neuen Befehlen die **neuen** Dateien mit einchecken.
7. **reqwest ohne `json`/`stream`/`gzip`, kein direktes `tokio`.** `.json()` und `tokio::time::sleep`
   kompilieren nicht. Entweder beim Muster bleiben (`serde_json::to_vec`, `response.chunk()`,
   `spawn_blocking`) oder Features bewusst ergänzen (jedes zieht Bauzeit auf drei Systemen nach).
   `rustls::crypto::ring::default_provider().install_default()` vor dem Client-Bau nicht vergessen.
8. **SHA-1 und base64 sind nicht direkt eingetragen.** `ring` und `base64` in `Cargo.toml` aufnehmen
   (beide schon in `Cargo.lock`, gleiche Versionen wählen: `ring = "0.17"`, `base64 = "0.23"`), sonst
   ändert sich `Cargo.lock` und `cargo test --locked` bei GitHub scheitert, bis die Datei mit
   eingecheckt ist.
9. **Weiterleitungen und der Schlüssel.** Alle drei Clients schränken Weiterleitungen ein, damit der
   Schlüssel nur an eine Adresse geht. Für GitHub: Standard `Policy::none()`; nur falls das Archiv
   genutzt wird, die Weiterleitung von Hand und **ohne** Schlüssel verfolgen. Test dazu wie
   `legendkeeper.rs` 536–558.
10. **Pfade aus dem Repository sind fremde Eingaben.** Immer durch `store::resolve` bzw.
    `media::path_of`; nie selbst Pfade zusammensetzen. Groß-/Kleinschreibung: macOS und Windows
    unterscheiden sie nicht, Git schon – zwei Pfade, die sich nur darin unterscheiden, würden sich
    gegenseitig überschreiben (als Konflikt melden). Dateinamen mit Umlauten sind erlaubt
    (`store.rs` 384–385) – macOS liefert sie teils zerlegt (NFD), Windows zusammengesetzt (NFC):
    Die Kennungen der Dokumente sind zwar ASCII, aber der Vergleich von Pfaden sollte das aushalten.
11. **Der Wächter meldet eigenes Schreiben mit** (`watch.rs` 5–6). Beim Holen vieler Dateien kommen
    Meldungen in Schüben; die Oberfläche liest dann jede Datei einzeln nach (`store_read` je Pfad,
    `db.ts` 335). Bei Tausenden Dateien (Erstabruf in einen **offenen** Spielstand) wäre das träge –
    der Erstabruf gehört deshalb auf den Startbildschirm, **bevor** die Kampagne geöffnet wird.
    Ein Abgleich, der hochlädt, darf umgekehrt nicht durch die Wächter-Meldung seiner eigenen
    Stand-Datei wieder ausgelöst werden (deshalb versteckt oder außerhalb des Ordners).
12. **Schlüsselbund auf dem Mac ungeprüft** (2.4): behelfsmäßige Signatur → vermutlich Passwortdialog
    nach jeder neuen Version. Abgleich beim Öffnen darf daran nicht hängen bleiben; Fehler
    `NoStorageAccess` leise als „Abgleich ruht – Schlüsselbund gesperrt“ zeigen.
13. **Kein `Toaster`/`ConfirmHost` im Startbildschirm** (`AppShell.tsx` 426–427 vs. `Welcome.tsx`):
    `toast()` und `confirmDialog()` bleiben dort unsichtbar bzw. lösen nie auf. Meldungen im
    Startbildschirm stehen als Zeilen im Panel (`Welcome.tsx` 163–170).
14. **Fehler als Satz erkennen ist brüchig** (`errors.ts` 138–142 sucht nach „nicht erreichbar“ usw.).
    Für „ohne Netz läuft alles weiter“ eine Art mitliefern, nicht Sätze auslesen – und `invoke` in
    `platform.ts` 35–42 entsprechend erweitern (heute wird jedes Nicht-Text-Fehlerobjekt zu
    „Unerwarteter Fehler in der App.“).
15. **Vorschau im Browser:** kein Schlüsselbund, kein Ordner, CSP/Netz anders. Abschnitt mit einem Satz
    zeigen („Der Abgleich arbeitet nur in der installierten App.“), nichts aufrufen; Logik über einen
    übergebbaren Boten testbar halten. `?welcome` zeigt den Startbildschirm auch dort.
16. **Texte, die vom „Cloud-Laufwerk“ sprechen**, widersprechen der Entscheidung des Spielleiters
    (kein Cloud-Laufwerk): `ProblemsSection.tsx` 46–63, `store.rs` 64, `config.rs` 1–2,
    `data/store.ts` 2–3, `watch.rs` 1–2, `lib.rs` 29. Beim Bau mit anfassen – sichtbar sind davon
    `ProblemsSection` und der Satz aus `store.rs` 64.
17. **„Konfliktkopie“ ist schon ein Begriff im Programm:** `db.parseDoc` (`db.ts` 117–123) lädt keine
    Datei, deren Name nicht zur Kennung passt, und `explainProblem` (`einstellungen/model.ts` 95–110)
    erkennt Namenszusätze wie „konflikt“, „(1)“, „ - kopie“. Legt der Abgleich die fremde Fassung je
    als Nebendatei ab, erschiene sie dort als „Problem beim Laden“ – entweder bewusst nutzen
    (verliert nie etwas, übersteht einen Absturz) oder solche Dateien versteckt ablegen.
18. **Prüfungen bei GitHub kosten Freiminuten** (macOS zehnfach): jede Änderung unter `src-tauri/**`
    löst den Dreifach-Lauf aus. Rust-Änderungen bündeln; lokal `cargo test --locked` vor dem Hochladen
    (und Rückgabewert prüfen, nicht durch eine Pipe schicken – Memory „Vor dem Sichern Rückgabewert prüfen“).
19. **Ein anderer Kollege schreibt gerade an `src/features/abend` und `src/domain/prep.ts`** im selben
    Arbeitsbaum – der Abgleich berührt davon nichts; `AppShell.tsx` (Zeichen in der Leiste) und
    `einstellungen/index.tsx` sind die einzigen geteilten Dateien, die angefasst werden müssen.
